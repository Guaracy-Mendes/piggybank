# Synthetic payment rail contract

`bank-rails` is the typed protocol and bounded HTTP adapter; `provider-simulator` is its independent persistent fixture. This contract implements SIMULATED/TST only. All URLs must use loopback HTTP. Requests time out at 1.5 seconds, redirects are rejected and response bodies are bounded to 64 KiB. It is not a real payment rail integration.

| Provider endpoint | Request | Response / financial meaning |
| --- | --- | --- |
| `GET /rails/recipients/{reference}` | `X-Rail-Key` | Signed, current recipient availability and currency; no account or financial authority |
| `POST /rails/instructions` | Signed `RailInstruction` | Signed `RailEvidence`; ACCEPTED/PENDING acknowledges the saved instruction only |
| `POST /rails/inquiry` | Original signed instruction | Original current evidence; NOT_FOUND is an observation, never proof permitting hold release |
| `POST /rails/cancellation` | Original signed instruction | Immutable CANCELLED tombstone for an unknown instruction, or the existing final result; delayed submits cannot execute a cancelled identity |
| `POST /admin/rail-scenarios` | `X-Rail-Key`, `{instructionId, mode}` | Fixture fault configuration; no bank financial state is changed |
| `POST /admin/rail-events` | `X-Rail-Key`, `{instructionId, status}` | Advance a saved synthetic instruction; final states remain immutable |
| `POST /admin/rail-credits` | `X-Rail-Key`, `CreditEvidence` | Persist and sign an immutable synthetic incoming or return event; bank validation remains independent |
| Bank `POST /api/v1/providers/simulated/payments` | Signed `RailEvidence` or `CreditEvidence` | Live authentication, durable deduplication and acceptance (`202`); asynchronous Core booking/allocation |

The local default rail key is separate from the controls simulator key. Runtime overrides use `BANK_RAIL_SIGNING_KEY` and `BANK_RAIL_PROVIDER_BASE`. Signed packets contain `{timestamp, signature, body}`. HMAC-SHA256 covers the timestamp, a newline and the canonical JSON SHA-256 fingerprint, with a URL-safe unpadded Base64 signature. Live authentication accepts only a 60-second timestamp window. Exact typed scope validation follows signature verification.

`RailInstruction` uses camelCase fields: `instructionId`, `paymentId` (equal stable economic UUIDs), `beneficiaryReference`, `amount`, `requestedDate`, `inputDigest`, `rail`, `authorityUntil`. Amount uses `{minorUnits: "1234", currency: {code: "TST", scale: 2}}`. Minor units are canonical i64 decimal strings. The input digest binds the complete immutable bank instruction, including quote, fee, recipient/product/policy versions and payer. `SIM` plus 32 uppercase hexadecimal digits identifies a synthetic external recipient. The seeded reference is `SIM00000000000000000000000000000001`. First acceptance requires a currently enabled recipient, the UTC business date and unexpired authority; replay/inquiry preserve the originally saved result after expiry.

`RailEvidence` contains `evidenceId`, `provider` (`SYNTHETIC_RAIL`), `instructionId`, `paymentId`, `inputDigest`, `amount`, `status`, `version`, `occurredAt`, `settlementDate`, `reasonCode`. The adapter verifies exact identity, digest and amount, positive version, bounded reason code and dates. SETTLED requires a settlement date. All other statuses forbid it. Provider evidence versions and immutable final states are protected in PostgreSQL. Reusing an instruction ID with any changed business input fails. The bank retains authenticated evidence by payment/version and detects conflicting repeated versions.

`CreditEvidence` contains `eventType` (`INBOUND_SETTLED` or `RETURN_SETTLED`), `movementId`, `evidenceId`, `provider`, `rail`, `originalPaymentId`, `receivingReference`, `amount`, `businessDate`, `occurredAt`, `version` (1), and `reasonCode`. Amount must be positive TST. Incoming events require a `PB` plus 32 uppercase hexadecimal receiving reference and no original payment. Returns require the original payment ID and no receiving reference. Future dates, invalid types and changed immutable identities fail validation. A valid signature does not authorize an over-return: Core serializes total accepted principal against the settled original. The simulator intentionally supports signing such faulty inputs for bank rejection tests.

The bank stores original authenticated packets. On later retries, Core verifies their integrity and typed financial scope without reapplying the live ingress timestamp window. It never replaces the provider signature with a bank-generated packet. Evidence IDs are unique across outgoing finality and incoming/return credits. Conflicts are immutable quarantine records with owned cases. Final outgoing financial receipts, suspense movements and allocation receipts provide separate durable recovery points.

Settlement consumes the exact submitted hold and books principal plus fee once. Definitive rejection/cancellation releases it once. Incoming funds first enter controlled suspense; current customer checks and destination restrictions gate allocation. Returns preserve the original journal, refund principal only and retain gross daily usage. An HTTP `202` or a provider acknowledgment proves neither booking nor customer availability.

Modes are `ACCEPT`, `REJECT`, `LOST_RESPONSE`, `BEFORE_ACCEPT_TIMEOUT`, and `CONFLICT`. LOST_RESPONSE commits one acceptance before delaying longer than the adapter deadline. BEFORE_ACCEPT_TIMEOUT does not persist acceptance. CONFLICT signs an altered amount for scope-rejection tests without changing saved provider history. Inquiry recovers original evidence. Provider instructions/events survive process restarts. Bank-side durable cancellation requests and aged operator reconciliation use the same original instruction and financial receipts; see the [recovery runbook](../../../docs/runbooks/payment-recovery.md). An active fault scenario can still delay transport after cancellation; clearing a synthetic transport fault does not change the provider's immutable financial result. File ingress and real provider authentication are not enabled by this synthetic HTTP contract.
