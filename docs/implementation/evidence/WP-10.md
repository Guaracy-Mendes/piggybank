# WP-10 — Authoritative financial Core evidence

Verified locally on 2026-10-23 with `make test-integration`, `make migrate` and `make app-check`. The Core crate and security-definer PostgreSQL routines implement exact TST minor-unit balances, durable holds, immutable balanced journal batches, unique operation/posting identities, business-key recovery and linked full-reversal corrections.

Twenty concurrent reserves against 1,000 units admitted exactly ten 100-unit holds. Internal transfer consumed one hold and posted both legs in one transaction. Equivalent retries returned the same batch; altered funding conflicted. An intentionally restricted recipient rolled back hold consumption, payer balance, journal and outbox. Overflow and empty/unbalanced commits were rejected. Runtime roles cannot edit balances, holds, journal rows or invoke the owner-only generic posting primitive. Triggers also reject owner mutation of committed journal history. Accounts are locked in stable UUID order.

Hold changes and journal facts commit in Core's own outbox. Pre-submission release is idempotent. A submitted unknown hold cannot be released through the implemented public Core method and remains reserved; authenticated evidence-backed release is integrated with the rail lifecycle later. Synthetic funding uses balanced clearing/customer movements and is explicitly local-only.

Full reversals require a current workforce proposal and an independent canonical-person approval bound to the original batch. Missing approval, self-approval, another batch, a second economic reversal and revoked checker authority were rejected. A correction preserved the original and appended one linked balanced batch, with safe retry by original command key. The owning Core runtime is a trusted internal principal; channel authentication/authorization remains at application entry. Actual chart, provider settlement, Finance mapping and production policy qualification remain separate packages.
