# WP-35 completion evidence

WP-35 was completed on 2026-11-18 as migration `0069_atm_channel.sql` (schema 69), as a **local synthetic R2
capability** against a network simulator role. See the [channel supplement](../atm-channel.md) and the
[acceptance README](../../../tests/acceptance/atm/README.md). A real network, its certification and enablement need
DEC-04, DEC-09 and WP-32.

## Delivered behavior

1. **Channel supplement.**
   - Balance inquiry and cash withdrawal are enabled. Every other ATM operation is declined explicitly with no
     effect.
   - Per-withdrawal and daily limits, and a 120-second authorization lifetime.
2. **Channel authentication.**
   - HMAC-signed network messages and signed responses, plus a required PIN assertion.
   - Synthetic card tokens linked by owners to their own accounts, usable only while the holder still owns the
     account, and blockable by the customer.
3. **Bounded financial effects.**
   - The authorization id is the Core operation for the hold and for the single `ATM_WITHDRAWAL` posting.
   - Duplicate messages replay the stored signed response, and message-id reuse conflicts.
   - Duplicate completions post once. A reversal before completion releases the hold; a late reversal is flagged,
     never posted.
   - The worker expires timed-out authorizations.
4. **Common restrictions.** Core's hold and posting re-check account state, debit blocks and funds, so customer
   and assisted freezes decline ATM withdrawals.
5. **Reconciliation.** A signed settlement file is classified item by item, with no netting.
6. **Clients.**
   - Customer portal: **ATM access** in Profile & security.
   - Staff portal: **ATM channel**.
   - Threat model: SF-005 (synthetic ATM network key).

## Failures before the final run

- **Missing intermediate state.** Without one, a retried authorization after a crash between the hold and the stored
  response would have minted a new authorization id, and with it a second hold. The schema gained `PENDING`, written
  first and keyed by the network message id.
- **Wrong database role.** The first build read Core tables through the payments role, which has no access to them.
  Those reads now use Core's pool.
- **Unfunded test account.** The browser journey's account had no funds, so the withdrawal was declined. The journey
  now funds it with the local synthetic tool.

Earlier runs, kept here, not hidden:
- **`.local/ci/20261118T180028Z`.** Failed at the resilience drills. In D5, native step-up begin returned 503 right
  after the issuer-pause drill (D4). The 503 comes from the step-up insert, meaning a database or pool error, not
  the issuer. It did not reproduce in an isolated rerun or in the next two pipeline runs. The drill harness now keeps service
  logs in `.local/resilience-logs/`. The root cause, a WP-27 two-`clock_timestamp()` CHECK race, was found and fixed
  in WP-36 (see the [WP-36 evidence](WP-36.md)). No retry was added.
- **`.local/ci/20261118T181135Z`.** Failed at the consumer browser step: axe reported colour contrast on a
  *hovered* secondary button. This was a genuine, pre-existing defect: in `official.css` the generic dark-green
  `button:hover` rule out-ranked `button.secondary`, so hovered secondary buttons showed dark text on dark green.
  Fixed with a `button.secondary:hover` rule that keeps the paper background.
