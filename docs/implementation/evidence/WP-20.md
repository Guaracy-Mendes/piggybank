# WP-20 — Internal payments, exact quotes and action approval

Verified locally on 2026-10-27. The Payments module owns verified internal recipients, immutable quotes, one stable economic payment identity, confirmation and durable workflow scheduling. Core alone owns balances, fee booking, daily-limit use and immutable journal receipts. HTTP contracts describe 62 actual route patterns / 67 operations, with generated TypeScript integration in both browser clients.

Recipients explicitly share a Core receiving reference. Registration checks its current internal destination and never infers a person from email. Revocation/version changes invalidate unused quotes and serialize with execution. Quotes bind recipient, source product/pricing, exact principal/fee/total, UTC date and expiry. A quote has one payment intent. Reusing a request key with altered content conflicts. The enabled path is immediate INTERNAL/TST; external providers and future execution dates are separate packages.

Confirmation requires fresh issuer reauthentication for the original actor and the exact payment details. The customer sees a separate explicit confirmation step after returning from the issuer. Current source ownership/restrictions, recipient, quote, proof and signed sanctions/risk/fraud decisions are checked before execution. An unconfirmed request, a changed proof digest, a revoked recipient and a current denial produced no booking. Core checks expiration again after waiting for account locks.

Principal, fee and daily principal-budget use commit together under ordered Core account locks. A priced fixture debited 10,032 minor units, credited the recipient 10,000 and the fee control account 32, with the entire ledger still summing to zero. Concurrent payments exceeding a 15,000 daily principal cap booked only one of two 10,000 instructions. Runtime roles cannot directly change financial tables. Quote, recipient, instruction and execution identities/history are protected from alteration/truncation.

The lost-acknowledgement test stopped after Core committed but before Payments recorded completion. Retrying the original instruction recovered the same immutable execution receipt and journal batch, without a second financial effect. Even an expired execution permit can recover an already committed matching receipt; it cannot authorize new effects. A forged SETTLED orchestration row without that Core receipt is not exposed as financial completion. Workflow completion and the payment's business outcome remain distinct.

The real Chromium workflow opened accounts for two distinct customers through persistent onboarding, funded the payer with a balanced fixture posting, shared a receiving reference, reviewed the quote, completed actual issuer reauthentication, explicitly confirmed, observed signed controls and booked the internal transfer. Source/recipient balances were exact, altered/unapproved/foreign requests were rejected, repeated confirmation preserved the booking, and fresh issuer login resumed the original payment/journal reference. A separate workforce session inspected the same booking with current inquiry role and payments queue membership. Desktop/mobile screenshots were inspected; layout and accessibility scans passed.
