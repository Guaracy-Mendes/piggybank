# WP-23 — Unknown-outcome recovery, cancellation and reconciliation

Verified in the synthetic local environment on 2026-10-31. Recovery commands are immutable, actor/client/key scoped and bound to the original payment and exact operator reason. Current ownership or payment inquiry/operator roles and queue membership are rechecked when accepting the command. Business acceptance precedes Platform scheduling; retries recover the same command and job after a lost acknowledgment. The worker preserves the original provider instruction, economic ID, full digest and authority scope.

Cancellation serializes with execution on the original intent. Before possible submission it releases only the bound unsubmitted reservation; loss of that release acknowledgment recovers without a provider send. After possible submission it uses the original signed cancellation protocol and the shared fenced transport lease. A concurrent live submit/inquiry retains its lease until completion. Provider cancellation tombstones prevent late submission of the same identity. Only definitive signed nonexecution and a Core release receipt produce CANCELLED. Cancellation after settlement preserves the original batch, reports that it was too late and cannot refund or release consumed funds.

Unknown/NOT_FOUND results and expired authority never expire submitted money into release. Each durable job defaults to eight attempts; new explicit operator inquiries have a 30 second cooldown. Exhausted recovery retains funds with an owned payment case. A further authorized audited command can continue recovery. Core finality/booking lookup precedes new effects and recovers lost booking or release acknowledgments. False orchestration terminal claims on active submitted commitments are restored conservatively to unknown before original-identity inquiry.

Reconciliation reads independent Core reservation, hold, aggregate held balance, booking and daily-budget facts. It compares scope, owning workflow, provider work and evidence, terminal claims and age. Orphaned commitments, inconsistent totals and submitted holds older than the selected synthetic five minute threshold become stable owned cases. Expected asynchronous work/receipt/acknowledgment gaps have a 30 second grace period. A second Core finality read defers snapshots that changed between module reads. This avoids opening investigations for ordinary processing windows. Changed observations append immutable history and audit. Matching preserves both the investigation and its history; it does not close a financial case or authorize money changes.

Persistent cursor pages of 50 cover financial positions, payment continuations, credit continuations and recovery commands. A real database test places 51 unresolved incoming receipts behind lost scheduling acknowledgments and verifies both pages recover exactly 51 original jobs. Another test seeds an orphaned submitted commitment and a held-total mismatch using the disposable fixture's migration principal; the bank creates owned diagnostics and releases nothing.

The real browser flow exhausts/ages an original synthetic instruction, recovers it through operator inquiry, rejects cross-customer cancellation/history access, preserves the journal after late cancellation and confirms a separate submitted cancellation with unchanged booked balance and zero held funds.
