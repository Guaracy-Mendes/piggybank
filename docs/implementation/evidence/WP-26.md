# WP-26 completion evidence

WP-26 was completed on 2026-11-17 as migration `0063_operations_monitoring.sql` (schema 63), within its local synthetic scope. The [specification](../operations-monitoring.md), [runbook](../../runbooks/event-replay.md) and [acceptance manifest](../../../tests/acceptance/operations/README.md) give the details.

## Delivered behavior

1. **Transaction monitoring (FR-CTRL-04, AT-30).** Versioned fixture rules are evaluated once per durable projected journal fact.
   - Alerts are anchored to the earliest operation in their window, with overlap suppression. Duplicate or conflicting events, stream replays and retrospective scans yield one alert per economic episode.
   - Each alert opens a `MONITORING` case that is not visible to the customer.
   - Disposition needs a proposer and a different approver, both attributable; dispositions are immutable.
2. **Data quality (FR-DATA-05).** Eight checks run every 30 seconds:
   - missing projected journal facts, quarantined events and broken references
   - stale projection watermark (NFR-08 display) and undelivered outbox events
   - provider backlog, aged reconciliation breaks and failed messages

   Each finding has one owned alert with a `DATA` case and a next action. The alert clears automatically when the condition ends, and a steward's acknowledgement closes the case. Projection repair writes only the Data read model, and the Data role is denied any balance or journal write.
3. **Operations reporting and correlation (FR-CTRL-05, FR-OPS-02).** Operations snapshots are taken in one `REPEATABLE READ` transaction and stored with a digest. Traces correlate journal, payment, events, cases, alerts and notifications by durable identifiers only.
4. **Notifications.**
   - One message per economic or document identity, deduplicated by key.
   - Mandatory and optional purposes, with recorded preference history and suppression evidence.
   - Fixed safe templates (no amounts, balances, full identifiers or token material) and masked recipients.
   - Synthetic capture with outage drills, bounded backoff, six attempts, and an owned alert on exhaustion.
5. **Clients and runtime.**
   - Staff: **Operations monitor** page.
   - Customer: **Notifications → Messages** and **Message preferences**.
   - Worker: monitoring and notifications every 5 seconds, data-quality scan every 30 seconds.
   - API: 13 typed routes in OpenAPI and the generated client.
   - Roles: `operations.view`, `data.steward` and `events.replay` capabilities; the local seed grants `data_steward`.

## Failures before the final run

These are retained here, not hidden:
- **Name clash in the draft migration.** A PL/pgSQL output column shadowed a table column in `quality_findings`; resolved with `#variable_conflict use_column`.
- **Over-strict test expectations.** Three integration assertions assumed counts that were wrong:
  - Retrospective "existing" counts.
  - Undelivered events in other modules' outboxes.
  - A rescan opening a new undelivered-events alert, caused by the scan's own case events while the threshold is zero.

  The tests now assert the intended behavior.
- **Light-mode contrast.** The first browser run found that the WP-25 statement figures failed contrast in light theme (earlier runs used dark mode). They now use the paper background.
- **Approver section access.** Approvers lacked one section, and a single failing request blanked the whole page. Approvers may now read message status, and each section loads independently.
- **Browser poll timing.** A poll counted elements before the asynchronous load finished; it now waits for the section.
- **Formatting.** The first gated `app-check` failed on formatting only; `cargo fmt` fixed it before the migration was applied.
