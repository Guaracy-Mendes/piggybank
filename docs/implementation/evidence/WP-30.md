# WP-30 completion evidence

WP-30 qualified the local, single-host synthetic environment on 2026-11-17 and 2026-11-18. It covered acceptance,
capacity, fault and recovery. The full results are in the [local qualification report](../local-qualification.md).
The [acceptance manifest](../../../tests/acceptance/manifest.json), [load suite](../../../tests/load/README.md) and
[resilience drills](../../../tests/resilience/README.md) make them reproducible.

## Delivered

1. **Branch-level acceptance (FR-OPS-04).**
   - `tests/acceptance/manifest.json` covers 30 scenarios and 54 branches, validated by `make acceptance`
     (`scripts/acceptance.py`).
   - Status counts: PASS 41, FAIL 1, PENDING 7, NOT_APPLICABLE_R1 5.
   - Every PASS and FAIL branch references evidence in the repository. Every non-PASS branch states its reason.
     `--strict` exits non-zero while any branch fails.
2. **Reproducible workload (NFR-02 to NFR-05).**
   - `bank-load http` is an open-loop generator with native virtual users and rotating refresh tokens.
   - `bank-load core` runs concurrent Core transfers with idempotent replays.
   - `tests/load/run.py` checks financial invariants before and after, records peak database connections, and runs
     named NFR checks. Targets: `make test-load` and `make test-load-measured`.
3. **Fault drills.** `tests/resilience/drills.py` (D1–D5, `make test-resilience`, a gated CI step):
   - worker crash and outbox replay;
   - API crash during durable commands;
   - broker outage;
   - issuer outage;
   - rail provider outage during submission.
4. **Capacity fixes found by qualification.**
   - CF-01: the `authorization` and `controls` audit streams are split into 16 shard chains, verified by
     `AuditLog::verify_sharded`.
   - CF-02: the quota counter is a single-statement upsert, committed asynchronously.
   - CF-03: `BANK_DB_POOL_MAX` sets the per-module pool size.
   - Fixture and runner: the fixture can run release binaries, and the load runner refuses to measure a foreign
     fixture.

## Failures and corrections during qualification

These are kept here, not hidden:
- **Debug builds.** The first load smoke used debug binaries and missed every rate. Release builds are now the
  default.
- **Overlapping runs.** One measured run was invalid: a diagnostic burst I had started was still running, and the
  new fixture's readiness check was answered by the old fixture's API. That run was discarded, and the runner now
  refuses to measure a fixture that has exited.
- **Wrong first diagnosis.** I first attributed the burst ceiling to the control-check audit stream. Sharding it
  alone changed nothing (46/s). Sampling the live database then identified the `authorization` stream, and sharding
  that raised throughput to 63/s at the same pool size.
- **Weak drills, tightened.**
  - D2 first killed the API before any command had been acknowledged. It now waits for at least 3 acknowledgements
    and asserts that some commands were still in flight.
  - D5's settlement count first joined on the wrong key. It now asserts exactly one settlement batch.
