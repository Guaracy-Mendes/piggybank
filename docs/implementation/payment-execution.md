# Payment execution implementation

WP-20 starts with INTERNAL transfers in TST, immediately on the UTC quote business date. WP-21 adds immediate SIMULATED outgoing submission; future execution dates remain disabled. WP-22 adds authenticated finality, incoming payments and original-linked returns. WP-23 adds durable cancellation requests, bounded operator recovery and owned financial reconciliation. Public interfaces expose exact principal, fee, total debit, dates, stable identities and actual financial status.

The receiving customer creates an opaque Core receiving reference and shares it explicitly. Registering a beneficiary resolves this reference against an active credit-enabled Core account; it does not search customers by email or legal identity. Beneficiary revocation/version changes invalidate unused quotes. Quotes bind the source account's published product/pricing version, recipient account, beneficiary version, date, exact amount/fee and expiration. They are immutable. A quote can create one stable payment intent. Reusing a request key for a different quote fails.

Confirmation requires fresh issuer reauthentication bound to the exact payment details and original payment identity. The BFF keeps issuer material server side. An accepted intent is persisted before durable scheduling; the worker can recover an acknowledgement loss without creating a new payment. Current ownership/restrictions, beneficiary state, quote, approval and signed sanctions/risk/fraud decisions are checked again before execution. Manual review retains the original provider decision and original payment/workflow identities. Expired or denied instructions do not debit funds.

Core alone commits principal, fee and daily-limit usage. Sorted account locks serialize available funds and the payer's UTC daily principal budget. The journal credits the recipient principal, credits the synthetic fee control account when applicable and debits the payer's exact total in one transaction. Direct journal/table writes remain unavailable to runtime callers. An immutable payment execution receipt binds the complete request fingerprint to the journal batch. After a lost response, that receipt recovers the original committed result even when the original quote has since expired. SETTLED is recorded only against that booking evidence.

The internal path needs no externally submitted hold: debit, credit, fee and limit use commit together. The external rail packages add reservations, provider instruction identity, uncertain-outcome recovery and evidence-backed settlement/release without changing the internal receipt guarantee. A workflow's completed status is separate from its payment's business outcome; completed declined/expired processing does not imply settled money.

WP-21 adds an approved effective SIMULATED policy with a per-payment limit and an explicit synthetic UTC 24/7 calendar. The payee for the Core reservation is the fixed synthetic settlement account. External recipient availability is authenticated by a separate rail protocol at registration and quote/confirmation. Provider acceptance checks current availability again. A pause immediately prevents new submissions under the policy lock; independent, exact revision-bound approval is needed to resume. Policy publication preserves an existing emergency pause. Seed configuration uses the same independent approval ports.

Before a possible provider call, Core reserves exact principal plus fee and the gross daily principal budget. The budget includes both committed internal payments and active external reservations. Holds, request digests and reservation authority are immutable financial facts owned by Core. Payments stages stable provider work, marks Core submitted, then commits its attempt marker and fenced short lease before HTTP. Calls occur outside a database transaction. Responses recheck fencing after acquiring locks. A crash after Core marks submission but before Payments saves its work is recovered conservatively by reconstructing the original instruction and inquiring; it cannot trigger a blind second send.

A response loss retains the original instruction and submitted hold. Inquiry uses the same durable input after provider/process restarts, quote expiry or an emergency pause. NOT_FOUND never proves nonexecution and never releases submitted funds. The provider deduplicates by immutable full request identity. ACCEPTED/PENDING is shown as acknowledged and pending, with no journal receipt; booked balances do not change, and held funds reduce availability. Bounded exhausted retries create an owned payment case.

The provider posts signed evidence to `POST /api/v1/providers/simulated/payments`. The ingress authenticates a live packet before typed scope validation and durable acceptance. A successful `202` acknowledges durable evidence, not a completed credit or debit. Duplicate evidence has the same immutable financial identity. Changed versions or cross-type evidence-ID reuse cannot overwrite history; authenticated conflicts are quarantined with an owned Controls case. The workforce inquiry shows safe quarantine summaries; authentication material is never returned to browser clients. This selected synthetic protocol uses HTTP callbacks; a file adapter is not enabled.

Core independently verifies the archived packet's HMAC and exact original instruction binding. A SETTLED result consumes the submitted hold and commits one balanced payer/principal/fee journal, the daily-budget POSTED fact and an immutable finality receipt atomically. A later debit freeze does not discard an already submitted financial commitment. An authenticated REJECTED or CANCELLED result releases that exact submitted reservation without a debit. A receipt recovered after a lost Core acknowledgment is authoritative even when the workflow still says RECONCILING. A delayed acknowledgment cannot downgrade settlement, and contradictory final evidence cannot release consumed funds. Generic reversals of these movements are forbidden.

`INBOUND_SETTLED` and `RETURN_SETTLED` carry distinct immutable movement and evidence IDs. Core first posts clearing to suspense. For a known destination, Payments derives the customer identity from Core and requests current signed payment checks; allocation from suspense to the customer then rechecks the account and exact trusted permit under Core locks. Unknown references, closed or credit-restricted accounts and review/deny outcomes retain funds in suspense with an owned case. Only an allocation receipt makes funds available. Repeated callbacks, worker retries and lost allocation acknowledgments recover the same suspense/allocation batches. The API cannot claim CREDITED without Core evidence.

Returns require an authenticated settled external original payment. All accepted returns, including amounts still in suspense, share an original-payment lock and cannot exceed its principal. Each return has new linked suspense and allocation journals; the original journal and settlement state remain immutable. Partial and multiple returns accumulate in `returns.received`, while `returns.credited` reports actual allocations. Fees are retained, and gross daily principal usage remains POSTED. Customer and staff views show the original payment with a separate return summary and correction history.

An owned, unconfirmed DRAFT can be cancelled without financial side effects. The API advertises `CANCEL_DRAFT` only for that state. Confirmed instructions advertise `CANCEL_PAYMENT` when eligible. Cancellation is a separate durable request; its acceptance never means funds have been released. Before possible submission it serializes with execution and can release a bound unsubmitted reservation. After possible submission it uses the same saved instruction, provider identity and fenced transport lease. A provider cancellation tombstone prevents a delayed submit from executing. If settlement already committed, cancellation reports that it was too late and preserves the original journal. Lost release acknowledgments recover the original financial receipt.

Workforce recovery requires current inquiry and operator roles plus the payments REVIEW queue. An immutable reason and actor-scoped request key bind each command. New inquiries have a 30 second cooldown. Jobs have bounded attempts and exhausted work retains the original hold with an owned case. Automatic finality recovery reads the original receipt before any new effects. A false orchestration failure on an active submitted hold is conservatively restored to unknown; only subsequent financial evidence can resolve it.

Reconciliation reads Core's independent reservation, hold, booking and daily-use facts, including aggregate held totals, and compares them with owning intent and provider work/evidence. Missing owners/work, mismatched amounts/digests, terminal claims without financial receipts and submitted holds older than the synthetic five minute threshold create stable owned breaks. Changed observations append immutable history and audit. Matching records preserve their cases. Persistent pages of 50 cover payment, credit, command and financial-position recovery without starvation behind old unresolved work. No observation or operator inquiry can edit a journal or authorize expiry release.

A same-key creation replay also recovers the original approval challenge when the Payments intent committed before its Controls challenge/link acknowledgment. Concurrent callers receive the same pending challenge while the draft remains eligible. This recovery does not mint issuer step-up proof, bypass current authority or post money. Terminal/expired observations retain their existing read behavior.
